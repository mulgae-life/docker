====================================================================
 인스턴스 yaml 키 레퍼런스
====================================================================

instances/<name>.yaml 1개 = vLLM 프로세스 1대. 이 문서는 모든 인스턴스
yaml이 공유하는 키 설명 + 모델별 노하우다. yaml에는 키당 제목 한 줄
주석과 "기동 실패 유발" 함정(주의)만 두고, 상세는 여기를 본다.

[복붙 규칙] 인스턴스를 추가할 땐 같은 모델군 yaml을 복사해 값만 바꾼다.
주석은 모든 파일에서 동일하므로 손대지 않는다. 모델을 바꿀 땐
(gemma <-> qwen) 아래 "모델별 값"의 블록을 통째로 교체한다.


── 자동 매칭 (gateway_port) ─────────────────────────────────────────

vLLM에는 전달되지 않는 메타 키. gateways/<port>.yaml의 discover_from이
instances/를 스캔해 이 키가 자기 게이트웨이 포트와 일치하는 인스턴스만
backends로 등록한다(vllm_server_launcher.py:_LAUNCHER_KEYS가 vllm serve
인자에서 제외). 같은 gateway_port 인스턴스가 여러 개면 LB 라우팅 대상.


── 모델 / 양자화 ────────────────────────────────────────────────────

  model
      HF 모델 ID. 런처가 download_dir과 조합해 로컬 경로 해석
      ({download_dir}/{model}). 폐쇄망은 런처 사용 필수(자동 오프라인
      모드) 또는 HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1.
  download_dir
      모델 로컬 저장 루트. 기본 /models/LLM.
  quantization
      fp8: BF16 체크포인트를 로딩 중 FP8로 온더플라이 양자화(캘리브레이션
      불필요). L40S(Ada)는 FP8 W8A8 공식 지원, 메모리 ~2x↓·처리량 ~1.6x↑.
      사전 양자화 모델(예: Qwen3.6-27B-FP8)은 생략(자동 감지).
  dtype
      활성화 dtype. auto = config.json 따름(권장).
  served_model_name
      API에 노출되는 모델명. 미설정 시 model에서 자동 추출한다.
      전 인스턴스가 [gemma-4]로 고정돼 있다 — 백엔드 모델을 Gemma/Qwen/GLM으로
      교체해도 사용자에게는 같은 이름만 보이게 하기 위해서다. 값을 바꾸면
      .env의 CHAT_MODEL·HF_MODEL도 함께 바꿔야 한다.
      리스트에 이름을 여러 개 넣으면 전부 /v1/models에 노출되고 요청에서도
      전부 받아들여진다. 응답 body의 model 필드와 메트릭 라벨은 첫 번째 값이다.
      실제 체크포인트 경로는 /v1/models의 root에 남으므로, 그것까지 가리는 일은
      게이트웨이 compat.mask_model_path가 맡는다.
  fingerprint_mode / fingerprint_value
      응답의 system_fingerprint를 무엇으로 채울지. 전 인스턴스가
      custom + gemma-4로 고정돼 있다.
      기본값 full이면 vllm-<버전>-tp<N>-<설정해시8>이 실리는데, 이 해시에
      모델 정체성이 들어가서 백엔드를 교체하면 값이 바뀐다 — 응답만 모아 봐도
      교체 시점이 외부에 드러나므로 served_model_name 고정과 충돌한다.
      none(필드 생략)이 아니라 custom을 쓰는 이유는, 클라이언트가 이 값을 로그·
      캐시 키로 쓰고 있을 때 null이 들어가면 깨질 수 있기 때문이다.
      원래 용도(seed와 짝지어 결정성 변화 추적)는 연속 배칭에서 성립하지 않는다.
      배경과 실측은 VLLM_OPS_GUIDE.md §10.5 참고.
  trust_remote_code
      모델 코드에 custom Python 포함 시. Gemma 4/Qwen3.5/3.6은 네이티브
      지원이라 불필요.


── 서버 ─────────────────────────────────────────────────────────────

  host
      바인딩 주소. 외부 0.0.0.0 / 내부 127.0.0.1. PII 프록시 뒤 인스턴스는
      127.0.0.1 (vLLM 직행 우회 차단). 0.0.0.0 유지 시 방화벽에서 이 포트
      외부 차단 필수.
  port
      vLLM 인스턴스 포트(내부 hint). 클라이언트는 gateway_port로 접근.
      사용 중이면 launcher가 +1, +2… 비어있는 첫 포트로 자동 회피, 실제
      포트는 instances/.runtime/<name>.json에 기록되고 게이트웨이가 그
      파일을 우선 참조. -> LB 인스턴스 복붙 시 port를 깜빡 안 바꿔도 자동 분리.
  uvicorn_log_level
      HTTP 서버 로그 레벨.


── GPU / 메모리 ─────────────────────────────────────────────────────

  gpus
      사용 GPU 번호 목록. 예) [0]+tp1=GPU0 단독, [0,1]+tp2=TP=2.
  tensor_parallel_size
      텐서 병렬 크기(gpus 개수와 일치). 멀티 인스턴스 LB는 같은
      gateway_port yaml 추가로 확장.
  gpu_memory_utilization
      GPU 메모리 비율(0~1) = vLLM이 쓸 총 예산. 이 예산 "안에" 가중치 +
      활성화 피크 + CUDA graph + KV 캐시가 모두 들어간다.
        KV = (total × util) − 가중치 − 활성화 피크 − CUDA graph
      활성화 피크는 기동 시 max_num_batched_tokens 크기로 forward를 1회
      돌려 실측한다(v1/worker/gpu_worker.py:442, v1/worker/utils.py:408).
      KV가 남는 전부를 가져가므로 util을 올리면 KV만 늘고 활성화 여유는
      그대로다 — 오히려 (1-util) 완충이 줄어 OOM에 취약해진다.
      ▸ (1-util)은 "활성화용 예약"이 아니다. CUDA 컨텍스트·드라이버 몫이며,
        프로파일 추정을 넘어선 활성화가 흘러넘치는 완충으로 쓰인다. 이
        완충까지 소진되면 torch.OutOfMemoryError로 워커가 죽는다.
      ▸ 여유 점검:
          ① 기동 직후 사용량 = nvidia-smi
          ② 활성화 가용     = 물리가용 − ①
          ③ 필요 활성화     = 부하 중 관측 or OOM 로그의 in-use − ①
        ② < ③ 이면 터진다. 이론 추정은
          max_num_batched_tokens × intermediate_size × 2B × 4~5.
      권장 0.85(멀티모달 큼) ~ 0.92(가중치 큼). 멀티모달 대형 배치가 들어
      오는 인스턴스는 0.9 이하로 둔다.


── 추론 ─────────────────────────────────────────────────────────────

  max_model_len
      컨텍스트 길이(프롬프트+출력 합산). KV 캐시 메모리에 따라 상한이
      정해짐 — GPU 메모리 표 참조.
  max_num_seqs
      동시 처리 시퀀스 수. ↑면 처리량↑·개별 지연↑. 멀티모달은 encoder
      cache 용량에 맞춰 제한.
  max_num_batched_tokens
      배치 최대 토큰 수(2의 배수 권장, max_model_len보다 작아도 chunked
      prefill이 자동 분할). 멀티모달은 encoder_cache_size와 동일값으로
      복제(scheduler.py:235). 이미지 1장 ≈ 16384 encoder tokens.
      max_num_seqs ≤ encoder_cache_size / 이미지 토큰 유지가 encoder
      cache race 방어선.
  seed
      재현용 전역 시드.


── Thinking / 샘플링 ────────────────────────────────────────────────

  default_chat_template_kwargs.enable_thinking
      챗봇 기본은 false(불필요한 reasoning 토큰·지연 감소). 형식 —
      Gemma 4 <|channel>thought<channel|>, Qwen3.5/3.6 <think>…</think>.
  default_chat_template_kwargs.reasoning_effort
      Qwen3.8 신규. thinking을 켠 호출에서 사고 길이를 조절한다.
      허용값 xhigh / medium / low 3개뿐 — 그 외 값은 채팅 템플릿이
      raise_exception을 던져 HTTP 400이 된다(chat_template.jinja:47-49).
      vLLM 최상위 reasoning_effort 필드는 none/minimal/low/medium/
      high/xhigh/max 7개를 통과시키므로, 스펙상 유효해 보이는 high가
      Qwen3.8에선 그대로 400이 된다. Gemma 4·Qwen3.5/3.6 템플릿에는
      이 변수 자체가 없어(grep 0건) 값을 줘도 무시된다(에러 아님).
      ▸ medium 권장. 템플릿 기본값 xhigh는 지시문으로 "가정을 검증
        하고 대안을 검토하라"를 주입해 생성량이 늘어난다(1회 실측:
        같은 질문에 medium 1673 → xhigh 4092 토큰). medium은 지시문을
        넣지 않는 중립값, low는 "짧게 끝내라"를 주입한다.
      ▸ enable_thinking: false면 템플릿이 effort 분기 자체를 타지
        않아 잘못된 값을 줘도 에러 없이 통과한다(실측).
      ▸ 우선순위: 요청 최상위 reasoning_effort > 요청 chat_template_
        kwargs.reasoning_effort > 이 yaml 기본값. 상세 VLLM_OPS_GUIDE
        §12.5.
  샘플링 기본값
      모델 generation_config.json이 vLLM 기본을 덮어씀. Gemma 4
      temp 1.0/top_k 64/top_p 0.95, Qwen3.5/3.6 temp 0.6/top_k 20/
      top_p 0.95. vLLM 순정값을 쓰려면 --generation-config vllm. 보통
      모델 권장값을 쓰고 호출에서 개별 오버라이드.


── 성능 ─────────────────────────────────────────────────────────────

  enable_prefix_caching
      반복 시스템 프롬프트 KV 재사용 -> TTFT 감소. 챗봇 필수급.
  kv_cache_dtype
      auto(모델 dtype 따름) / fp8_e4m3(KV도 FP8 -> 메모리 절반, 2배 용량;
      추론은 정밀도 중요해 e4m3 일택, e5m2는 학습용).
  language_model_only
      true면 이미지/오디오 허용량 0으로 강제 -> 멀티모달 프로파일링/예약
      메모리 절약.


── Speculative Decoding (★ 모델별로 정반대 — 주의) ──────────────────

Gemma 4 — 외부 drafter 기반 MTP
  - *-it-assistant drafter(31B용 0.5B / 26B-A4B용 0.4B, BF16, Apache 2.0)를
    별도 다운로드. target과 embedding 테이블 + 마지막 layer activation
    공유하는 specialized draft model.
  - speculative_config.model의 "${model}"은 런처가 본체 model 값으로 치환
    (launcher의 문자열 치환 — vLLM 기능 아님). "${model}-assistant"로 쓰면
    본체 모델명만 바꿔도 drafter가 자동 추종 — cp 후 본체/drafter 짝
    어긋남(31B 본체 + 26B drafter 등) 구조적 차단.
  - 주의: method 키 명시 금지. vLLM 0.20.2(config/speculative.py:613-628)는
    eagle/eagle3/dflash/draft_model만 직접 받고, mtp는 자동 감지 결과로만
    설정된다. method: mtp를 명시하면 else 분기 -> NotImplementedError:
    Unsupported speculative method.
  - 자동 감지 조건: vLLM ≥ 0.20.2(PR #41745, gemma4_mtp 추가) +
    transformers ≥ 5.8.0(gemma4_assistant model_type 등록). 충족 시
    drafter model_type 자동 감지로 method="mtp" 자동 설정.
  - 권장 num_speculative_tokens: E2B 2 / E4B 4 / 26B-A4B 4 / 31B 4–8(느린
    target일수록 큰 값). 알려진 이슈 #41789(31B MTP acceptance 0.2% 보고)는
    본 환경 라이브 실측 70~85%로 재현 안 됨(2026-07-13 gemma 로그).
  - 26B-A4B(MoE) 주의: ① drafter 이득은 동시성 4+에서 유효 — 저배치는 매
    토큰 다른 expert 활성화로 로딩 비용 발생(공식 overview) ② 4-bit 양자화
    금지 — expert 차원 704가 작아 품질 붕괴(공식 레시피), 8-bit(fp8 /
    int8_per_channel_weight_only)만 사용 ③ MXFP4 런타임 양자화 크래시
    (#39000) -> fp8 대체 ④ data_parallel_size>1 크래시(#38999).
  - 출처: vLLM PR #41745(2026-05-06 merge, v0.20.2), Issue #42005,
    vLLM Gemma4 recipes·ai.google.dev MTP overview(2026-07-21 재확인).

Qwen 3.6 — native MTP (drafter 불필요)
  - 사전·사후 학습에 MTP 포함된 native MTP 모델. 메인 모델 자신의
    sequential MTP head로 draft 생성(DeepSeek-V3 계열 구조). 별도
    체크포인트 불필요.
  - 주의: method: mtp 직접 명시. Qwen 모델카드는 qwen3_next_mtp를
    권장하나 vLLM 0.20.2가 deprecated 처리하고 런타임에 mtp로 자동
    치환(speculative.py:456). upstream 정본 표기 mtp를 명시한다.
  - 주의: num_speculative_tokens 보수값. 모델카드 권장 2지만 vLLM 0.20.2가
    ">1이면 같은 MTP layer를 여러 번 forward해 acceptance rate 저하 가능"
    경고(speculative.py:602). 보수 시작값으로 두고 acceptance rate/TPOT
    모니터링 후 상향.
  - 알려진 이슈(본 환경 검증 필요): #38182(MTP 활성 시 prefix cache hit
    92%->71%), #39323(FA3 backend 회귀 -> FLASHINFER 권장). 동시성 16+
    배치 +24% throughput, prefill-bound −7% 회귀.
  - 출처: vLLM v0.20.2 실로그(speculative.py:456,602), Qwen3.6-27B-FP8
    HF 모델카드.


── 멀티모달 ─────────────────────────────────────────────────────────

  mm_encoder_tp_mode
      data: vision encoder를 TP 쪼갬 대신 data-parallel 처리(통신
      오버헤드↓). Qwen3.5/3.6 공식 레시피. 미지원 모델은 vLLM이 weights로
      자동 폴백(안전).
  mm_processor_cache_type
      shm: 전처리된 멀티모달 입력을 shared memory FIFO로 공유 -> IPC
      직렬화/메모리 중복 제거, zero-copy. TP=2 + 멀티모달 동시 요청에서 이득.
  mm_processor_kwargs
      모델별 동작 다름.
      ▸ Gemma 4: { max_soft_tokens: N } — vision soft token 예산.
        주의: 허용값 70/140/280/560/1120 외엔 sys.exit(1) 기동 실패
        (gemma4_mm.py:474-485 validator). 70≈썸네일, 280=기본(~800×800),
        560=문서·차트 QA 시작점, 1120=OCR. 2×면 이미지당 KV/prefill 선형 증가.
      ▸ Qwen3-VL: {}(빈 dict). max_soft_tokens는 Gemma 전용이라 Qwen에선
        WARNING+자동 드롭(무효). Qwen은 min_pixels/max_pixels/fps 별도
        체계. 혼란 방지로 빈 dict 유지.
  limit_mm_per_prompt
      프롬프트당 멀티모달 입력 상한(모델 독립 공용 키). 낮추면 encoder
      cache/예약 메모리 절약. 챗봇 권장 image=4~5.


── 멀티모달 안정성 ──────────────────────────────────────────────────

  async_scheduling
      true면 scheduler step과 model execution 파이프라인화로 TPS 5~15%↑.
      단 scheduler 장부와 worker encoder cache 간 1-step 시차로 멀티모달
      eviction 시 race -> Encoder cache miss assertion 크래시(2026-04-18
      GPU0_1 크래시 원인, vLLM 0.19.0).
      주의: 멀티모달 사용 시 false (TPS 포기, 안정성 선택).
  disable_chunked_mm_input
      Mamba-hybrid 모델(예: Qwen3.6-35B-A3B)에서는 설정 금지. prefix
      caching ON 시 vLLM이 mamba_cache_mode='align' 자동 적용(config.py:441)
      -> attention block_size를 1056 등으로 확장 -> MM 입력을 block_size
      배수로 쪼갤 유연성 필수. disable_chunked_mm_input=True는
      validate_block_size()(vllm.py:1730)가 AssertionError로 거부. 이
      모델군 encoder cache race 방어선은 async_scheduling: false +
      max_num_seqs ≤ encoder_cache_size/이미지 토큰 두 개로 충분
      (2026-04-18 재기동 실패 후 제거).


── 로깅 ─────────────────────────────────────────────────────────────

  enable_log_requests
      true면 INFO에 요청 ID/파라미터, DEBUG에 프롬프트. 운영 false.
  disable_log_stats
      false=처리 통계(TPS/큐/지연) 출력. 병목 분석 시 false 유지.


── 런처 전용 키 (vllm serve에 전달되지 않음) ────────────────────────

  env
      dict. launcher가 vllm serve 서브프로세스 환경에 머지한다. 모델별
      권장 환경변수를 yaml 한 곳에서 관리하기 위한 키.
      ▸ PYTORCH_CUDA_ALLOC_CONF: "expandable_segments:True"
        기본 할당자는 고정 크기 세그먼트를 쓰므로, 프리필(수천~수만 tok)과
        디코드(수 tok)가 번갈아 오면 자투리가 쌓여 총량이 남아도 큰 연속
        블록을 못 잡는다. 이 옵션은 CUDA VMM으로 세그먼트를 확장 가능하게
        만들어 단편화를 없앤다. 연산 커널은 그대로라 속도 영향 없음.
        ⚠️ KV connector(Nixl/Mooncake) 사용 시 vLLM이 기동을 거부한다
           (config/vllm.py:730-768) — RDMA 등록 주소가 재매핑되므로.
      ▸ VLLM_DISABLE_COMPILE_CACHE: "1"  (Voxtral 등)
  auto_restart_max
      vllm serve가 비정상 종료(rc≠0)했을 때 launcher가 자동 재기동할 최대
      연속 횟수. 기본 3, 0이면 비활성.
      ▸ 재기동 전에 해당 GPU의 잔여 VLLM::Worker_TP*를 정리한다. 엔진이
        죽어도 워커는 CUDA 컨텍스트를 쥔 채 남아 GPU 메모리를 반환하지
        않으므로, 정리 없이 재기동하면 메모리 부족으로 실패한다.
      ▸ backoff 10s → 30s → 60s(이후 60s 유지). 300초 이상 가동한 뒤 죽었
        으면 새로운 장애로 보고 연속 실패 카운터를 초기화한다.
      ▸ SIGTERM(`./start.sh down`)으로 내린 경우는 재기동하지 않는다.
  watchdog_unhealthy_seconds
      /health 무응답이 이 시간만큼 이어지면 launcher가 vllm serve를 강제
      종료해 재기동 경로로 넘긴다. 기본 90, 0이면 비활성.
      ▸ 필요한 이유: EngineCore가 죽으면 API 서버가 "Finished server
        process" 로그까지 찍고도 워커를 기다리며 수 분간 잔존하는 경우가
        있다. 이때 proc.wait()가 반환되지 않아 auto_restart_max만으로는
        재기동이 발동하지 못한다.
      ▸ 감시는 한 번이라도 health 200을 받은 뒤에 시작한다. 모델 로딩(수
        분)을 장애로 오판하면 기동 자체가 불가능해지기 때문.

── GPU 메모리 참고 (gpu_memory_utilization=0.95 기준) ────────────────

⚠️ 표를 고르기 전에 인스턴스가 어느 환경인지 먼저 본다. GPU가 다르면
   같은 tensor_parallel_size라도 결론이 뒤집힌다.
     연구계(이 컨테이너)  L40S 46GB, 2장 묶어 TP2  → qwen / gemma / gemma-26b
     개발(테스트)계·운영계 RTX PRO 6000 96GB 1장 TP1 → prd-*
   기준 환경은 RTX PRO 6000이다. 연구계가 L40S 2장인 것은 여기 GPU가
   L40S뿐이라 96GB 1장을 2장으로 대신하는 것이다.

RTX PRO 6000 96GB × 1장 (개발·운영계 — prd-* 기준)
  모델                 가중치    KV Cache 가용   권장 max_model_len
  26B-A4B FP8 (온라인) ~26 GB    ~57 GB          65536~131072
  31B FP8 (온라인)     ~29 GB    ~54 GB          65536~131072
  27B FP8              ~27 GB    ~56 GB          65536~131072
  ※ 계산 추정치다. 기동 로그의 "Available KV cache memory" /
     "GPU KV cache size"로 실측 확정할 것.

L40S 46GB × 2장 (tensor_parallel_size: 2 — 연구계)
  모델               가중치    KV Cache 가용   권장 max_model_len
  31B FP8 (온라인)   ~29 GB    ~58.4 GB        65536~131072
  27B FP8            ~27 GB    ~60.4 GB        65536~131072
  실측(gemma-26b, util 0.9, max_model_len 32768):
    Available KV cache memory 20.53 GiB/GPU, GPU KV cache size 195,633 tokens

L40S 46GB × 1장 (참고 — 이 구성으로 운영 중인 인스턴스는 없다)
  모델               가중치    KV Cache 가용   권장 max_model_len
  31B FP8 (온라인)   ~29 GB    ~14.7 GB        12288
  27B FP8            ~27 GB    ~16.7 GB        12288~16384
  14B BF16           ~28 GB    ~15.7 GB        12288~32768
  8B BF16            ~16 GB    ~27.7 GB        32768~65536
  ⚠️ TP1이라고 이 표를 보면 안 된다. prd-*는 TP1이지만 96GB 표를 본다.
